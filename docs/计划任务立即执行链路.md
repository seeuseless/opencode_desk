# 计划任务立即执行链路

> 以代码为准，改动后同步。

## 关键触点

- `electron/main/scheduler.ts`：计划任务入口。创建会话后调用 `/session/{id}/prompt_async`，内核受理 prompt 后立即返回；`runningTaskIds` 仍防止同一任务重复启动。
- `electron/main/adapter.ts`：对 `message` 和 `prompt_async` 两种 POST 端点统一执行模型校正。
- `electron/main/index.ts` / `electron/preload/index.ts`：通过 `schedule:ran` 把已启动的会话 id 通知渲染层；通过 `schedule:reorder` 接收拖拽后的完整任务 id 顺序。
- `src/renderer/components/useDragSort.ts`：设置页与计划任务共用的原生 HTML5 竖向拖拽逻辑；只有手柄发起拖拽，按目标行上下半区计算真实插入位置。
- `src/renderer/App.tsx`：收到 `schedule:ran` 后补拉内置「任务」目录会话；立即执行启动后只展开左侧「任务」目录，不切换当前会话窗口。
- `src/renderer/components/SchedulesView.tsx`：立即执行按钮只在“请求内核受理”期间显示转圈，执行期间的模型任务由会话行状态表示；任务左侧手柄支持拖拽排序。

## 排序约定

- `ScheduleTask.order` 越小越靠前；`readSchedules()` 始终按它升序返回。
- 旧版 `schedules.json` 没有 `order` 时，按 `createdAt` 倒序初始化；后续任一写盘操作会把新顺序保存回去。
- 新建任务取当前最小 `order - 1` 并插到首位，保证默认最新任务在上；编辑保留原位置，删除不重排其余任务。
- 拖拽提交完整有序任务 id，主进程校验集合后重排并把 `order` 压紧为 `0...n-1` 落盘。

## 错过执行时刻的补跑

电脑关机 / 应用没开导致错过执行点时的行为，全在 `normalizeTask()` 读盘归一化那一步决定（两个阈值）：

- `STALE_MS = 3 × TICK_MS`（90s）：超过才算「当时应用没在跑」，而不是正常 tick 抖动。窗口内的一律保留 `nextRun` 原值，走正常执行。
- `CATCHUP_WINDOW = 24h`：错过超过这么久就不再补，读盘时把 `nextRun` 推进到下个周期。

分派规则：

| 情况 | 读盘时 `nextRun` | 结果 |
|---|---|---|
| 刚过点（< 90s） | 保留原值 | 正常执行，标题 `[计划] 名` |
| 错过 90s ~ 24h 且 `catchUp` 开（缺省开） | **保留原值** | 启动后第一轮 tick 补跑，标题 `[补跑] 名（原定 YYYY-MM-DD HH:mm）` |
| 错过 90s ~ 24h 但 `catchUp` 关 | 推进到下个周期 | 本次不补 |
| 错过 > 24h | 推进到下个周期 | 本次不补 |

要点：

- **只补最近那一次**。连续错过多次也只跑一遍：`claimSchedule()` 在执行前就把 `nextRun` 推到未来，补跑后不会立刻再触发第二次。
- `catchUp` 缺省视为**开**（`t.catchUp !== false`）：老存档没有这个键，不该因为「没记录过」就一律不补。
- 内核未启动时 tick 整轮跳过且不动 `nextRun`，所以补跑会一直挂起到内核起来为止。
- 补跑会话标题前缀是 `[补跑] `，与 `[计划] ` 不同 —— 渲染层用 `oc.ts` 的 `isScheduleSession()` 同时认这两个前缀（`Sidebar.tsx` 的日期角标、`ChatView.tsx` 的 `isSchedule`），否则补跑会话会从左栏任务列表里漏掉。
- `ScheduleRan.catchUp = { at }` 带着原定时刻推给渲染层，但**不弹窗**：`App.tsx` 的 `notice` 是阻塞式 Modal，启动时为一条提示弹框太吵，辨识交给标题里的「[补跑]…（原定 …）」。
