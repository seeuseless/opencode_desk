# 发版与更新提示

给用户装好的青鸟发一个新版本时，走「改版本号 → 打 tag → CI 出包」三步。
用户那边的「设置 → 关于」会自动看到更新提示，点两下就完成升级。

## 一、发版（维护者）

> ### ⚠️ 前置条件：仓库必须是公开（public）的
>
> 应用**不携带、也不该携带 GitHub 凭据**，它对 GitHub 是匿名请求。而匿名访问非公开仓库时
> GitHub 一律返回 **404**（不是 403）——所以仓库只要是 private，检查更新就永远失败，
> 且提示会写成「读不到发布信息：仓库未公开（或地址不对），也可能还没建过任何 Release」。
>
> **实测**（2026-09）：本仓库 `seeuseless/opencode_desk` 当前匿名访问返回 404，
> 而 `git ls-remote`（带本机保存的凭据）能正常列出 `master` / `v0` 两个分支 ——
> 说明它是**私有仓库**。发版前请先到
> <https://github.com/seeuseless/opencode_desk/settings> 底部把可见性改成 Public，
> 否则用户端「设置 → 关于」永远只能看到检查失败。
>
> 另一条实测记录：GitHub 对**未登录**的 API 请求按出口 IP 限流（共享网络下常见），
> 撞上时提示「GitHub 接口限流，稍后再试即可」。这不是代码问题，过一会儿就好。

```bash
# 1. 改版本号（唯一事实来源）
#    package.json 的 version 与即将打的 tag 必须对得上：
#    应用内「当前版本」读的就是安装包里的这个值，对不上会让用户一直看到"有新版本"。
vim package.json            # "version": "0.0.2"

# 2. 提交推送
git add -A && git commit -m "release: v0.0.2" && git push

# 3. 打 tag 并推送 —— 这一步触发 CI
git tag -a v0.0.2 -m "release v0.0.2"
git push origin v0.0.2
```

`.github/workflows/release.yml` 会在 `windows-latest` 与 `macos-latest` 上**并行**构建，
每个平台一次出**双架构**包（Windows x64 + ARM64、macOS Apple Silicon + Intel）：
`yarn install --frozen-lockfile` → `yarn dist` / `yarn dist:mac`（含 `electron-vite build`、
内核架构校验与 `electron-builder --x64 --arm64` / `--arm64 --x64`）→ 把六个安装包上传到
`v0.0.2` 这个 Release。交叉架构的包由 beforePack 钩子（`scripts/electron-before-pack.cjs`）
换入对应架构的 agent 内核，构建后校验读 PE / Mach-O 头断言「包架构 = 内核架构」。

跑完去 <https://github.com/seeuseless/opencode_desk/releases> 确认附件里有
**`QingNiao-Setup.exe`**（Windows x64 的固定名，名字必须完全一致，见下节）与
`QingNiao-Setup-arm64.exe`、`QingNiao-Setup-{arm64,x64}.dmg/.zip`。想给用户写点更新说明，
直接在 Release 页面编辑那一版的描述即可——应用里「发现新版本」区块显示的就是这段正文。

> 也可以在 Actions 页面手动触发（`workflow_dispatch`）补跑某个 tag：填 `v0.0.2` 即可。

## 二、用户端是什么体验

「设置 → 关于」一页搞定，全流程不需要用户去浏览器翻 Release：

| 步骤 | 界面 | 背后做了什么 |
| --- | --- | --- |
| 1 | 点「检查更新」 | 问 GitHub Releases 最新版，本地比对版本号（`updater.ts` 的 `isNewer`，非简单字符串比较） |
| 2 | 看到新版本号与更新说明 | 显示 Release 的 tag、正文、发布时间；「查看发布页」可去浏览器看完整内容 |
| 3 | 点「下载更新」 | 流式下载到 `~/.qingniaoai/updates/`，进度条实时走；可随时「取消下载」 |
| 4 | 点「立即安装并重启」 | 拉起刚下载的安装包（按机器架构认领的那份），**本应用随即退出**（安装器要求文件不被占用）；Windows 上 NSIS 装完会自动重新启动青鸟 |

macOS 那边 dmg 只能"挂载磁盘映像"，替不了你完成替换，所以第 4 步会改成
提示用户手动把青鸟拖进「应用程序」。

### 界面上刻意"不显示"的东西

这一页只回答两个问题：**我现在是什么版本、有没有新版能升**。其余一律不上界面：

| 不显示 | 原因 |
| --- | --- |
| **仓库地址（`github.com/seeuseless/...`）** | 用户不需要知道更新包从哪来，只需要知道"能升级"。地址只在「发现新版本 → 查看发布页」时按需打开，不在页面上铺开。`UpdateState` 里也已去掉 `repo` 字段，主进程只内部使用 |
| **「开发模式不检查更新」提示** | 源码跑的时候本来就是开发者自己在用，不需要向自己解释为什么没有检查按钮——**直接不渲染那个按钮**即可，不摆说明文字 |
| **「最新版本」空栏** | 没检查、或检查后确认是最新时，那一栏只能是"—"或"已是最新"，白占一行。改成：确认无新版时只在版本号右侧显示一个小小的 `✓ 已是最新` |
| **更新说明以外的元信息** | 不显示下载次数、校验值、文件哈希这类东西——那是给维护者看的，不是给用户看的 |

> 设计原则：**这一页是给普通用户的操作面，不是给开发者的信息面板。** 维护者需要的信息
> （仓库坐标、tag、附件名、产物大小）都在本文件与 Release 页面里，不进应用界面。

## 三、两个必须守住的约定

### 1. Windows x64 安装包文件名固定，不带版本号

`electron-builder.yml` 里 `artifactName` 带 `${arch}`（双架构产物不互相覆盖）：

```yaml
artifactName: QingNiao-Setup-${arch}.${ext}
# → x64: QingNiao-Setup-x64.exe  arm64: QingNiao-Setup-arm64.exe
#   mac: QingNiao-Setup-{arm64,x64}.dmg/.zip
```

**不要把 `${productName}` 或中文「青鸟」写回附件名**：GitHub 的附件名与
`releases/latest/download/<名>` 直链对非 ASCII 字符要 URL 转义，中文名在下载端不稳
（转义后地址对不上、部分环境直接拿不到）。只改产物文件名，**应用本身仍叫「青鸟」**
（`productName` 不变），快捷方式、开始菜单、窗口标题都还是中文。

因为应用内的"一键下载"用的是**固定地址**（仓库坐标写在 `resources/update.json`，
**不在界面上暴露**）：

```
https://github.com/<owner>/<repo>/releases/latest/download/QingNiao-Setup.exe
```

这条路不经过 `api.github.com`（国内常被阻断），`releases/latest/download/<固定名>`
是能直连的下载通道。因此 **x64 的包由 CI 构建后重命名回 `QingNiao-Setup.exe` 再上传**，
每次发版覆盖上传同名附件；**其余附件带 `-<arch>` 后缀**，应用内更新
（`updater.ts` 的 `pickAsset`）按当前机器架构 `process.arch` 精确认领。历史版本靠 git tag
与各自的 Release 页面追溯。

### 2. 版本号 = tag = package.json

| 位置 | 作用 |
| --- | --- |
| `package.json` 的 `version` | 打包进安装包，应用内显示为「当前版本」 |
| git tag（如 `v0.0.2`） | CI 触发条件；`updater.ts` 摘掉 `v` 前缀后与当前版本比较 |

两段式/三段式都支持（`v0.1`、`v0.0.2` 均可）。

## 四、检查更新失败怎么办

`updater.ts` **不编造版本号**：查不到就显示失败原因，并给一个「打开发布页」的出口。
常见原因与处理：

| 提示 | 原因 | 处理 |
| --- | --- | --- |
| `读不到发布信息：仓库未公开（或地址不对），也可能还没建过任何 Release` | 仓库是 private（匿名请求一律 404）；或仓库名写错；或只打了 tag 但没在 GitHub 上建 Release | 把仓库改成 Public / 检查 `resources/update.json` 里的 `repo` / 在 tag 上建 Release |
| `GitHub 接口限流（HTTP 403）` | 未登录的 API 限额按出口 IP 算，共享网络容易撞上 | 稍后重试；或点「打开发布页」自行下载 |
| 请求超时 / `fetch failed` | 网络不通（`api.github.com` 在国内常被阻断） | 点「打开发布页」自行下载；或配代理后重试 |
| `下载不完整（x / y 字节）` | 下载中途断流 | 重下（半截文件已自动删掉，不会留下坏包） |

> 检查更新只读 GitHub 公开接口，**不需要登录、不上报任何用户数据**。

## 五、免责声明与使用条款

「设置 → 关于」底部有一行条款入口，点击弹出完整正文。文案集中在
**`src/renderer/lib/license.ts`**，界面从这里取，不要在组件里另写一份。

要点：

- 定位是**把 MIT 协议的免责语言翻成用户看得懂的中文**，与 `LICENSE` 并行适用、
  不替代它（条款末尾写明了「不一致时以 MIT 为准」）。
- 不止一句"概不负责"，而是逐项点出真实风险：读写本机文件/执行命令、访问网络与第三方服务、
  调用第三方 AI 模型（勿当专业意见）、数据外发、接口费用——只写空泛免责既拦不住纠纷也不诚实。
- 末尾保留了「法定不可排除的责任（如故意或重大过失）不在此列」的说明：写死"一切责任全免"
  反而可能被整条认定无效。
- 条款改动时**同时改 `LICENSE_VERSION` 与 `LICENSE_DATE`**。这两个值**不在界面上显示**
  （用户看条款是为了知道\"我承担什么\"，摆一行「v1.0 · 2026-09-22」只会让人怀疑是不是过期了），
  它们只作为维护者的修订记录存在 `license.ts` 里。改完记得同步这段文档与 `library` 相关说明。

> 这份声明是技术性的风险告知，**不构成法律意见**。若将来涉及商业分发或有合规要求，
> 建议请律师按你实际经营主体与司法辖区重拟。

## 六、相关代码位置

| 文件 | 职责 |
| --- | --- |
| `electron/main/updater.ts` | 查最新版、版本比较、流式下载 + 进度、拉起安装包 |
| `electron/main/index.ts` | `update:*` 六个 IPC 通道；状态变化推给界面 |
| `electron/preload/index.ts` | 渲染层桥（`getUpdateState` / `checkUpdate` / `downloadUpdate` / `cancelUpdate` / `installUpdate` / `openRelease` / `onUpdateChanged`） |
| `src/renderer/components/UpdatePanel.tsx` | 设置 → 关于 界面（版本卡片、更新区块、条款入口与弹窗） |
| `src/renderer/lib/license.ts` | 免责声明正文（唯一来源，含仅供维护者用的 `LICENSE_VERSION` / `LICENSE_DATE`，不在界面显示） |
| `scripts/gen-update-meta.mjs` | 生成 `resources/update.json`（仓库坐标、tag 前缀；换仓库只改它） |
| `.github/workflows/release.yml` | tag → 构建 → 上传附件 |

> 之所以没有用 `electron-updater`：它默认要吃 electron-builder 生成的 `latest.yml`，
> 那份文件的大小/校验值必须与实际产物逐字节一致，手工维护极易失真。GitHub Releases
> 自带的 `tag_name` / `body` / `assets` 已经够用，少一份要维护的元数据。
